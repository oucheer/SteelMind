# 钢制家具 CRM 与多工厂 ERP 需求及架构方案

版本：评审稿 1.0。调研日期：2026-09-30。

## 1. 目标与决策

以成熟 ERP 为底座，贯通报价、订单、多工厂生产、库存分配、分批发货及财务，避免重新开发库存账和会计引擎。本次交付需求与架构文档，不代表已经安装、集成或验收任何系统。

已确认条件：

- 一家销售公司、多个自有工厂，不按每个工厂建立独立法人。
- 销售报价经确认转为订单。
- 首期成品报货，后续支持分工序报工。
- 成品按工厂及 SKU 统一入库，再分配给兼容订单。
- 支持分批发货，完整财务与成本采用完整规划、分期实施。
- 首期外部服务采用模拟与接口预留，不实际发送平台消息或签署合同。
- 未来可能向客户交付或销售软件；定制源码是否闭源尚未确定。

功能评估首选 ERPNext，Odoo Community 为授权与功能备选。不同时上线两套 ERP。正式选型必须通过实际业务验证及授权审查，不以仓库星数或模块目录存在作为通过标准。

## 2. 原始业务需求与分期

| 阶段 | 内容 | 交付边界 |
| --- | --- | --- |
| 第一期 | 产品客户、报价转订单、工厂任务、成品报货审核、库存预留调拨、分批发货、收付款、基础成本和报表 | 跑通订单到交付；不自动采集电商订单 |
| 第二期 | 采购、材料库存、BOM、工序报工、成本分摊、应收应付、结账与会计凭证 | 财务负责人确认核算制度后启用 |
| 第三期 | C 端知识库客服、B 端销售辅助、推广素材、合同辅助及真实平台适配 | 逐项核实平台授权和服务成本 |
| 独立验证项 | CAD 理解、空间布局与效果图、自动排产优化 | 先验证精度与约束，再纳入业务承诺 |

原始图片中的推广涵盖淘宝、天猫、京东、拼多多、小红书、抖音、百度和 GEO；内容涵盖产品图片、详情图、场景图及安装验收视频。第三期先建立素材、产品信息和发布任务管理，不默认各平台允许自动发帖或抓取。

C 端客服目标包括知识库回答、报价、合同及客户线索；B 端强调销售辅助、人工接管及定制需求。AI 生成报价和合同草稿，不自行确定交易条款、加盖电子印章或绕过人工审批。

### 3.3 授权门槛

- GPLv3 允许商业销售，但向客户分发时必须按适用条款履行许可证及对应源码义务；不得承诺所有 ERPNext 定制代码均可闭源。
- 独立扩展、API 集成与派生作品的判断不能仅以分仓库或分进程为依据，交付前请专业人员审查具体实现。
- Odoo 核心 LGPLv3 不等于所有模块均为 LGPL，不等于企业版功能免费，也不自动保证所有定制可闭源。
- 建立组件清单，记录版本、来源、许可证、修改、依赖、版权通知及源码交付方式。免费授权不等于零实施、运维或模型调用成本。
- 源码政策未明确前，只开展标准业务验证与文档设计，不签订不可履行的闭源交付承诺。客户合同必须明确安装方式、授权、源码和维护责任。

## 4. 角色、组织与权限

| 角色 | 主要职责 | 数据范围 |
| --- | --- | --- |
| 管理员 | 用户、权限、基础配置、审计 | 全局；高风险操作留痕 |
| 销售 | 客户、报价、订单、交期、收款查询 | 自己或授权团队的客户订单 |
| 生产管理 | 工厂任务、排期、报货审核、缺口处理 | 授权工厂及其任务 |
| 员工 | 提交个人报货、查看本人记录 | 本人及授权工厂；不看销售金额和客户电话 |
| 仓库物流 | 库存、预留、调拨、发货、物流 | 授权仓库及履约所需信息 |
| 财务 | 收付款、成本、核算、结账 | 财务授权范围 |
| 负责人 | 经营和交付看板 | 按授权汇总，不默认拥有所有写权限 |

工厂对应组织维度，仓库对应库存位置，成本中心对应核算维度。一个工厂可含成品、原料、待检等仓库。权限须同时约束列表、详情、导出、API 和附件，不仅隐藏页面按钮。

## 5. 核心业务规则

### 5.1 产品、报价与订单

- SKU 定义产品、规格、颜色及库存单位；订单保留规格快照，后续修改产品档案不改写旧单。
- 定制产品记录客户要求、附件及兼容标识，不能仅依赖自由文本判断库存是否可分配。
- 报价包含版本、有效期、数量、单价、折扣、税费和交期。确认人及时间留痕，同一确认请求只能生成一个目标订单。
- 已确认订单变更走变更记录及影响审核；已发货、已开票部分遵循底座取消、退货或调整机制，不直接覆盖。
- 销售订单明细可拆给不同工厂，分配数量总和不得超出有效需求；取消和跨厂重分配需处理原任务、预留及在途记录。
- 客户收货信息、联系人、物流及规格从订单产生，不让微信表格成为独立事实来源。

### 5.2 报货与入库

- 员工提交工厂、日期、SKU/定制规格、合格数量、待检或不合格数量及可选任务关联。系统生成本人日报；员工不能直接改库存。
- 状态为草稿、待审核、已审核、已驳回、已冲销。审核人不得无痕更改员工原始申报，修改要说明原因。
- 审核后通过底座受支持的业务操作生成入库单，记录报货与底座单据关联。重复审核不得重复入库。
- 一期尚未启用材料核算时，必须验证底座可支持的成品入库路径和财务影响。只能按财务批准的暂估价值入账，不能用零成本或伪造材料消耗冒充真实生产成本。
- 暂估值与实际成本明确区分。成本更正使用底座支持的核算流程，不能自行改写历史库存账；如果安全路径验证失败，相关库存过账必须阻断，先调整上线范围。
- 二期分工序报工优先复用 Job Card 等能力；仅最终合格产量进入成品库存，不能把各工序完成量相加为成品量。

### 5.3 库存、分配与调拨

- ERP 库存账为唯一来源。可用量由可分配库存减去有效预留得到，排除冻结、待检和不兼容产品。
- 预留必须关联销售订单明细、仓库和数量，并验证并发控制；不能由前端先读后写来防止超分配。
- 调拨包含调出、在途和调入确认，不能在两厂同时显示同一批现货。预留是否允许随调拨迁移需用固定底座版本实测，再形成操作规范。
- 订单、生产任务、现货及待入库量分别显示。生产完成不等于已入库，入库不等于已备货，备货不等于已发货。
- 退货先记录实际接收和质量判断，再决定重新入库或隔离；不自动释放为可售成品。

### 5.4 排期与发货

- 看板按需求、可用库存、已预留、任务未完成量及交期显示缺口。紧急标记由授权管理人员设置并留理由。
- 一期提供交期和缺口排序、人工排期及调整，不声称具有约束完整的自动最优排产。
- 发货可包含多订单明细或部分数量；物流记录承运商、运输方式、单号、发货日期及附件，未接接口时手工登记。
- 仓库确认底座出库单时扣库存、消耗相关预留；物流信息修改不再次出库。发货失败需可追查底座单据状态，禁止盲目重试。
- 生产、备货、发货和收款进度独立展示；订单结束需明确未交数量、退货、欠款和取消情况。

### 5.5 财务与报表

- 一期复用收付款单，记录预收、尾款、退款和核销关联；不能把订单总额与银行到账简单相减当作法定应收余额。
- 财务确定开票/记账时点、税口径、期初余额及应收政策。订单欠款展示管理口径，并与底座实际财务余额区分。
- 一期基础成本可采用批准的标准或暂估口径，利润看板必须标注口径及更新时间，不称为已结账实际利润。
- 二期纳入采购入库、采购发票、材料消耗、人工、制造费用、成本分摊、存货计价、期间结账和凭证。中国发票及财税报表单独验证或对接专业软件。
- 员工日报以日期和员工分组；产品汇总以工厂、日期、SKU/规格聚合；交付报表以订单交期、缺口及发货进度展示。
- 工序汇总不混入成品报货汇总；数量统一库存单位，金额注明币种与含税口径。

## 6. 复用映射与架构

| 能力 | ERPNext 候选对象 | 实现分类 | 验证要求 |
| --- | --- | --- | --- |
| 客户与报价转订单 | Customer、Quotation、Sales Order | 原生加配置 | 版本、权限、规格快照、重复转单 |
| 多工厂任务 | Work Order、Production Plan、仓库/成本维度 | 配置加扩展 | 拆单、跨厂权限及取消关联 |
| 员工报货 | 独立报货对象连接底座库存单据 | 行业扩展 | 审核、幂等、暂估成本与冲销 |
| 工序生产 | BOM、Operation、Job Card | 二期原生加配置 | 工序量与最终成品量分离 |
| 库存预留及调拨 | 底座库存相关能力 | 待版本验证 | 并发预留、在途、预留迁移 |
| 发货退货 | 底座销售出库相关单据 | 待实测确认 | 部分发货、退货、账务影响 |
| 收付款与凭证 | Payment Entry、Invoice、GL Entry、Journal Entry | 分期启用原生能力 | 核销、税口径、期初与结账 |
| 手机报货与交期看板 | 底座页面/独立扩展应用 | 最小必要定制 | 手机操作、权限、指标一致性 |
| 客服与 AI | Chatwoot/Dify 候选适配 | 三期可选 | 授权、人工接管、审计和隐私 |

建议结构：员工/销售/仓库页面 → 底座身份权限及独立行业扩展 → ERP 业务服务及唯一数据库；报表与外部适配只通过授权业务接口读取或提交。

不默认新增独立 NestJS 后端或第二套 PostgreSQL 业务账。ERPNext 使用其所支持的数据库和部署框架；选定版本后从官方兼容清单确认数据库、缓存、队列及镜像。定制优先独立 Frappe 应用，不修改上游核心。只有原生界面不能满足明确操作需求时，才加入轻量定制页面。

核心关系：客户 → 报价版本 → 销售订单及明细 → 工厂任务；报货 → 审核 → 底座入库；库存预留 → 订单明细；调拨 → 源仓库/目标仓库；发货明细 → 订单明细与出库；收付款/发票 → 底座核销关系。所有关联保留底座不可混淆的单据标识。

## 7. 扩展接口契约

以下是业务操作契约，不代表已建立 API。具体路由及类型根据最终底座制定，不绕过原生单据校验和权限。

| 操作 | 最小输入 | 输出及约束 |
| --- | --- | --- |
| 报价转单 | 报价 ID、确认版本、幂等键 | 订单 ID；重复请求返回同一结果，版本过期拒绝 |
| 报货提交 | 工厂、员工、业务日期、明细、幂等键 | 报货 ID、待审核状态；身份由服务端确定 |
| 报货审核 | 报货 ID、版本、批准明细、理由 | 入库关联及处理状态；权限、重复提交和失败恢复校验 |
| 库存预留 | 订单明细、仓库、规格、数量、幂等键 | 预留 ID；服务端并发校验可用量 |
| 发货确认 | 发货草稿 ID、版本、幂等键 | 出库单及关联；不能超过有效需求或合法可出库量 |
| 外部消息任务 | 业务单据、目标适配器、模板、幂等键 | 模拟/待发送/成功/失败状态；模拟不显示已真实发送 |

事务内同时保存业务关联与必要审计；外部调用使用持久任务或 outbox，由后台重试。超时先查询关联结果再重试，永久错误进入人工处理。敏感数据和密钥不得出现在普通日志中。

## 8. 外部服务边界

- 微信表格由系统导出，首期人工发送；模拟消息日志与真实消息明确区分。
- 淘宝、天猫、京东等逐平台核实商家权限、订单和客服开放能力，不采用未经授权的抓取或聊天模拟作为生产方案。
- 企业微信与私人微信分别评估，不能承诺私人微信自动加好友或无限制消息发送。
- 电子签约适配合法服务，明确签署人授权、印章管理、实名认证及证据留存；合同模板存在不等于可以自动盖章。
- AI 只接收权限允许且必要的数据，客户联系方式、CAD 和合同附件需明确服务商、保存策略及删除机制。模型输出必须允许人工接管。
- 知识库以审核产品资料为准，报价从授权业务数据获取；禁止 AI 编造库存、价格、交期、履约保证或发起未审批记账。

## 9. 实施任务及准入门槛

1. 确认交付模式和源码政策，完成 ERPNext、扩展及依赖授权检查；记录未决项。
2. 在隔离环境选择并固定官方兼容稳定版本，保存 tag、commit、镜像摘要及许可证。禁止用未经核验的 latest 直接生产部署。
3. 配置单公司、两工厂及必要仓库，建立最小客户、产品、报价和订单样例；验证原生链路。
4. 验证预留、跨厂分配、调拨、部分发货及成本影响；原生能力不满足时记录差距，而不是复制库存逻辑。
5. 验证一期成品入库和财务政策，由生产与财务共同确认。失败则调整实施范围或底座，不能以假账绕过。
6. 在独立扩展中实现手机报货、审核、任务关联、看板及导出，完成权限和重复提交测试。
7. 试运行、对账、备份恢复演练后再上线；二期财务及三期服务独立验收。

若 ERPNext 在许可或核心业务门槛上不适配，使用同一验收样例评估 Odoo Community；先确认社区功能与模块授权，再决定替换。不要只因核心 LGPL 就跳过功能测试。

上线前须确认：真实工厂和仓库、员工与审批关系、产品单位与定制编码、财务暂估/计价/税政策、期初余额、导入模板、数据清洗规则及客户交付合同。以上是业务待办，不作为已知事实虚构。

## 10. 验收测试

固定样例：常规 SKU A 订单 10 台，工厂一已有合格库存 3 台；分给两厂各生产 4 台及 3 台；全部审核后总可履约数量为 10 台，先发 6 台再发 4 台。另建规格不同的定制 SKU B 2 台、另一张竞争订单及一笔预收款。样例只用于测试，不代表真实客户数据。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| T01 | 报价重复确认、旧版本确认 | 同一请求只有一张订单；旧版本不能静默覆盖 |
| T02 | 两厂拆单与重分配 | 有效任务数量不超需求；取消处理关联记录 |
| T03 | 重复报货、重复审核、审核后更正 | 不重复入库；更正有冲销和审计链 |
| T04 | 两订单并发争用库存 | 预留不超过可用量，不靠页面刷新防超卖 |
| T05 | 定制规格错配 | 库存分配被拒绝，不靠肉眼备注判断 |
| T06 | 跨厂调拨 | 在途不重复可售；两端数量和账务可对账 |
| T07 | 分批发货 6 台及 4 台 | 只产生 10 台有效出库；重复确认不扣第二次 |

| T10 | 暂估成本及二期工序 | 不伪造消耗；工序量不累计成成品量 |
| T11 | 员工跨厂访问、导出及附件 | 无权限访问被服务端拒绝，客户和成本数据不泄露 |

## 11. 运维与交付

- 开发、测试、生产隔离；测试不使用未经脱敏的客户联系方式和合同。
- 密钥用部署环境的安全机制管理，最小权限 API 账号分适配器配置；管理操作保留审计。
- 对导入失败、单据关联失败、后台任务积压、库存异常和备份失败设置监控；通知对象与处理责任在上线前指定。
- 上线前完成全量备份和恢复演练，记录负责人及业务批准的恢复目标；未验证备份不允许上线。
- 数据导入先建立唯一标识、单位、期初库存和财务余额，抽样及总量对账，避免历史订单重复生成库存或财务流水。
